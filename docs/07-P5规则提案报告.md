## 1. 业务红线与落实方式

任务书 §4.3 的四条红线，逐条落到代码：

| 红线 | 落实点 | 验证 |
|---|---|---|
| 驳回原因**绝不直接写规则库** | 提案先落 `data/proposals/RP-*.json`；只有 `review_proposal(approve)` 才调用 `rules_store.approve` | 用例 A（批准前命中=False）、用例 E（驳回后指纹不变） |
| 去重：精确 / 包含 / 相似度>0.85 → 转修订 | `rules_store.find_similar` 三层检测（P2 校准：包含层加"覆盖率 ≥60%"约束） | 用例 C |
| 冲突：同模式异等级 → 转待裁决，禁止静默覆盖 | `conflict_check` 优先于去重；`approve` 对 `kind=conflict` 直接拒绝 | 用例 B |
| 审计复用条目内联字段，不建历史表 | 规则条目 `source/approved_by/approved_at/changelog` + `compliance_audit` 事件 | 用例 A5、F |

**额外加的一道关口**（P2 自检倒逼出来的）：`approve` 会拒绝**没有法条引用**的提案 ——
把"无引用不判风险"前移到写入关口，避免产出"永远命中却给不出依据"的规则。

## 2. 本阶段实测并修掉的一个真实缺陷

**并发审批时的文件读取竞态**：

- 现象：4 个线程同时审批同一提案，其中一个线程抛出未捕获的 `PermissionError`。
- 根因：认领采用"写临时文件 + `os.replace`"的原子替换；另一个线程可能刚好撞上替换瞬间，
  在 Windows 上读到被占用的文件。
- 处置：把提案读取封装为**带重试的读取**（最多 12 次、间隔 50ms），并在认领后**重新读取校验认领者**。
- 修复后：并发用例稳定通过，4 个请求中恰好 1 个成功、3 个得到
  「提案已被 supervisor-x@… 认领处理中，请勿重复提交」。

> 这与 P4 的 run 级互斥是**两层不同的锁**：run 级保护"同一份合同不被重复审批"，
> 提案级保护"同一条规则变更不被重复批准"。两者都用单条原子写实现，语义各自独立。

## 4. 设计取舍（与任务书二期边界一致）

明确**不做**的事，避免越做越大（任务书要求代码量控制在最小闭环）：

- 不做语义嵌入去重（一期用精确 + 包含 + difflib）

`status` 字段加灰度态，无需改动编排层。
