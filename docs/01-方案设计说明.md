## 1. 设计目标与约束

**目标**：在零改动外部运行时框架的前提下，交付一个可演示、可评测、可解释的岗位化合规数字员工。

**约束**：

| 来源 | 约束 |
|---|---|
| 环境 | Windows、无 Docker Desktop、无管理员权限；本地开发用免安装 PostgreSQL zip 前台进程 |
| 模型 | 统一走 OpenAI 兼容接口（DeepSeek） |
| 框架 | 源码零改动（见立项说明 §2） |
| 场景 | 低频高价值：日均 < 100 份，审批角色 ≤ 10 人 |
| 交付 | docker-compose 仅作交付物形态，不要求本机跑通 |

## 2. 总体架构

```
                    ┌──────────────── 输入 ────────────────┐
   飞书消息(主演示) ─┐                                      │
   Cron 例行扫描   ─┼─→ 外部运行时框架（进程A，源码零改动）  │
   Webhook/网关    ─┘        │                             │
                             ├─ 主 Agent（对话、HITL 通知接收、工具编排）
                             ├─ Workflow（后台线程池执行 + checkpoint）
                             ├─ Skills（岗位 SOP 注入）
                             └─ MCP 客户端 ──┐
                                             │ mcp__compliance__*
                                             ▼
                    ┌──────── 本项目 岗位能力服务（进程B）────────┐
                    │  MCP 工具层：解析 / 检索 / 标注 / 报告 / 提案 │
                    │  规则引擎：risk_rules.yaml（版本化）          │
                    │  法规库：向量 + BM25 混合检索 + 重排          │
                    │  证据链：trace_id / 规则版本 / 法条命中 / 操作者│
                    └───────────────┬────────────────────────────┘
                                    │
                    ┌──────── 网关（进程C，FastAPI）────────┐
                    │  认证与 RBAC · 统一待办队列 · SSE · 指标 │
                    └───────────────────────────────────────┘
                                    │
                    ┌──────── Mock 外部系统（进程D）────────┐
                    │  OA 文件服务 · 企业邮箱 · 故障注入开关  │
                    └───────────────────────────────────────┘
```

**关键说明**

- 框架侧只通过 `.lemonclaw/{.env,mcp.json,skills/}` 三个挂载点被配置，源码零改动。
- 岗位能力的真相源在本项目的 MCP 服务内，框架侧不持有业务规则。
- 网关**不复制**执行状态机：run 状态以框架的 run 表为准，网关只维护**待办视图**（人该做什么），避免双真相源。

## 3. 能力形态与工具契约

### 3.1 MCP 工具清单（本项目提供）

工具名遵循框架的 `mcp__<server_id>__<tool>` 约定，`server_id` 建议为 `compliance`。

| 工具 | 输入 | 输出（结构化） | 幂等键 |
|---|---|---|---|
| `parse_contract` | 文件路径/字节流、来源 | 条款列表（编号/标题/正文/页码）、表格（Markdown）、解析置信度、OCR 档位 | 文件内容哈希 |
| `extract_tables` | 文件路径、页范围 | 表格数组（含单元格坐标、合并信息） | 文件哈希 + 页范围 |
| `search_regulations` | 查询文本、top_k、过滤条件 | 命中条款（编号/来源/正文切片/相似度/重排分） | 查询哈希 |
| `annotate_risk` | 条款列表、检索结果 | 逐条标注（风险等级/命中规则ID+版本/关联法条/建议话术/依据链） | 条款哈希 + 规则版本 |
| `generate_report` | 审查上下文、标注结果 | 报告 Markdown/PDF 路径、执行摘要、指标快照 | run_id + 规则版本 |
| `propose_rule` | 驳回原因、合同 ID、操作者 | 提案对象（新增/修订、去重结果、冲突提示） | 驳回原因哈希 |
| `record_decision` | run_id、节点名、决策、操作者、意见 | 审计事件（append-only） | run_id + 节点名 + 操作者 |
| `list_pending` | 角色、状态 | 待办清单（供网关/主管视图） | — |

> **契约纪律**：每个工具必须返回**结构化 JSON**（不是自然语言），并携带 `trace_id` 与 `rule_version`；报告可读性由渲染层负责。理由：合规结论必须可追溯、可回归测试。

### 3.2 Workflow spec 映射

| 任务书节点 | 实际节点 kind | 说明 |
|---|---|---|
| intake（主 Agent 受理） | `main_agent` 或触发入口 | 渠道消息进入主 Agent，由其调用 `workflow_execute` |
| parse / retrieve / annotate | `tool` 节点 → `mcp__compliance__*` | 确定性环节，不让模型自由裁量 |
| 条件分支（风险等级） | `conditionals` + `router.kind=state_field` | 分支键必须是**离散字符串**（如 `high`/`mid`/`low`）；框架路由不支持数值区间与表达式 |
| 专员确认 / 修改 / 驳回 | `human` 节点 | 框架 human 节点输出字段默认 `user_input` |
| 修改后重新标注 | 循环边回到 annotate | 受 `recursion_limit` 保护，需验证收敛 |
| 主管复核 | 第二个 `human` 节点 | 需验证两个连续人工节点各自独立暂停/恢复 |
| 低风险直出 + 抽查 | 条件边 → 报告节点 → 抽查队列 | 抽查队列即统一待办表的低优先级条目 |
| 归档 | `tool` 节点 → `record_decision` | 报告落库 + 岗位经验写入框架记忆 + 证据链落盘 |

**图设计要点（来自源码事实）**

1. 每个节点的 `output_field` 必须显式命名并在 state_schema 中声明，避免默认值 (`output` / `user_input` / `agent_reply`) 造成字段碰撞。
2. `state_schema` 字段不要使用 `messages` 名字（reducer 语义特殊）。
3. 条件边的 mapping key 必须与路由返回值**完全相等**，否则静默走第一个分支——需在 D0 用反例验证。
4. 有状态字段（如多轮修改记录）显式挂 `append` reducer。

### 3.3 统一待办队列（本项目新增，替代"人肉带 run_id"）

框架的人工节点暂停后，通知文本里携带 `run_id`，依赖用户回复时**原样带回**才能恢复——这是框架的真实行为，直接用于生产会在"用户忘带 run_id"时静默卡死。

**本项目补的确定性路由层**：

```
待办表 todo（PG；SQLite 模式用同构表）
  todo_id / run_id / workflow_id / node_name / role_required
  title / summary / payload_json
  status(open|claimed|done|expired) / claimed_by / claimed_at
  idempotency_key(UNIQUE) / created_at / due_at / trace_id
```

- **生成**：`record_decision` 相邻的 `tool` 节点或后台轮询发现 `run.status=paused` 时写入待办。
- **消费**：网关按角色过滤展示；审批动作走"抢占式更新"（`UPDATE ... WHERE status='open'`），只有影响行数为 1 的请求获得执行权。
- **恢复**：由服务端调用 `workflow_resume(run_id, answer)`，`run_id` 来自待办记录，**不依赖模型从文本里抽取**。
- **重新通知**：进程重启后扫描 `paused` 的 run，为未完成待办补发通知（框架本身没有这个机制，见附录 A-6）。

## 4. 数据与存储

| 数据 | 存储 | 说明 |
|---|---|---|
| 合同原件与解析产物 | 文件系统 + 索引表 | 解析产物带文件哈希，避免重复解析 |
| 法规/内控条款（≥40 条） | 向量库（pgvector）+ BM25 | 混合检索 + 重排取 top-5；工具层做长度控制，不依赖框架记忆注入 |
| 风险规则 | `rules/risk_rules.yaml` | **唯一真相源**，版本化字段：`id/version/status/pattern/severity/priority/regulation_ref/suggestion/source/approved_by/approved_at/changelog` |
| 规则审计 | PG append-only 规则版本表 | YAML 由脚本生成（只读产物），diff 即审计链；避免并发写同一 YAML |
| 待办队列 | PG todo 表 | 唯一待办真相源 |
| 执行状态 | 框架 run 表与 checkpoint | 不复制、不改动 |
| 岗位经验记忆 | 框架记忆（Skills 之外的长期记忆块） | 被驳回的标注、人工修改沉淀为经验 |
| 证据链 | 每 run 一份 JSON + 索引 | `trace_id / 规则版本 / 法条命中 / 人工操作者 / 时间线` |

> **法规为什么不进框架记忆**：框架记忆的注入预算默认 1500 token、单块正文**硬截 200 字符**、检索采用纯词面 TF-IDF 且启动只装载 100 条——法条会被截断且同义改写即漏检。法规必须走本项目自建的向量检索。

## 6. 评测与验收口径

| 指标 | 定义 | 目标 |
|---|---|---|
| 预埋风险命中率 | 命中预埋风险条款数 / 预埋总数 | 报告实测值，不设虚高目标 |
| 误报率 | 误报条款数 / 被标注条款数 | 报告实测值 |
| 表格抽取准确率 | 单元格级正确率（人工抽检） | 单列指标，**与文本解析分开报** |
| 自动办结率 | 低风险自动完成数 / 总任务数 | 报告实测值 |
| 人审率 | 触发人工节点的任务数 / 总任务数 | 报告实测值 |
| 平均办结轮次 | 平均人工交互轮次 | 报告实测值 |
| 驳回原因分布 | 按原因分类的占比 | 用于规则演进 |

**评测集要求**：≥ 20 份合同（覆盖劳动合同/采购/租赁/金融销售/技术服务），每份定义固定标准答案（应命中条款、不应命中条款），逐项报告命中/漏报/误报。表格类合同（≥6 份）单独统计。

**测试分层**：单元（工具契约、规则解析与版本化、去重相似度、冲突判定、RBAC 鉴权、幂等键）、集成（端到端三路人工决策、断点续接、并发互斥、cron 触发、飞书往返）、异常注入（Mock 四类故障 × 降级路径）、**并发（现框架测试中并发用例为 0，本项目必须补）**。

## 7. 容错矩阵

| 异常 | 降级策略 |
|---|---|
| 模型超时/异常 | 合规链路使用独立低重试配置或外层熔断（框架默认 `max_retries=10`，单次失败最坏阻塞约 10 分钟，不能直接沿用）→ 任务转待办人工队列 |
| OCR/解析失败 | 高精度 OCR → 轻量 OCR → 无 OCR 模式；失败标记低置信度走人工，不阻塞批次 |
| 检索空/低分 | 降级为纯规则表标注，报告显式声明"未检索到适用法条" |
| 节点异常 | 依赖框架 checkpoint 保护，修复后恢复；副作用节点带幂等键 |
| Mock OA 超时/报错 | 重试 2 次 → 转人工队列 + 结构化日志 |
| 数据库故障 | 连接失败自动重连 + 告警日志；应用不崩溃 |
| 并发审批冲突 | 待办抢占式更新 + run 状态原子抢占，后到者收到"已被 XX 审批中" |
| 规则提案冲突 | 相似度超阈值转修订提案；同模式异等级强制人工裁决，禁止静默覆盖 |
| 通知投递失败 | 待办表 + 重试 + 幂等键（框架渠道无投递确认） |

## 8. 已知风险与规避

| # | 风险 | 事实依据 | 规避 |
|---|---|---|---|
| 1 | 人工恢复依赖用户手带 `run_id` | 通知文本显式要求 | 统一待办队列 + 服务端恢复 |
| 2 | 重启后无自动恢复/通知 | 框架 `list_pending_runs` 无生产调用点 | 启动扫描 paused → 补发通知 |
| 3 | 并发 resume 双跑同一 run | 状态检查与提交之间无原子抢占 | 数据库原子 CAS 抢占后再提交 |
| 4 | 长 SOP/法规被注入截断 | 技能正文超 10000 字符砍中间；记忆块截 200 字符 | 长知识走 MCP 工具检索，不进 system prompt |
| 5 | 报价单式"限流护栏"其实未实现 | 节点数/分支数/嵌套深度上限配置项无引用 | 不依赖；本层做输入校验 |
| 6 | 通知只有私聊通道、无投递确认 | 主动推送仅用用户 open_id；`chat_id` 未被使用 | 待办表兜底 + 群推不用（或改用其他渠道） |
| 7 | 数据库路径随启动目录漂移 | 库路径基于进程当前工作目录 | 部署脚本固定工作目录并校验 |
| 8 | 工作流初始化失败静默消失 | 初始化异常被吞、工具整体不注册 | 启动自检 + 健康检查暴露失败 |
| 9 | 模型重试放大阻塞 | 客户端重试 10 次 × 超时 60s | 合规链路独立低重试实例 |
| 10 | 表格抽取质量不可控 | 无现成基线 | 表格设为一等公民指标，独立评测 |
