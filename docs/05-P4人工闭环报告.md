## 1. 本阶段交付：`service/review_orchestrator.py`

把 P3 里"脚本扮演服务端"的部分固化为正式服务层，供网关、渠道与定时任务调用：

| 方法 | 职责 |
|---|---|
| `intake(doc_text/path, submitted_by)` | **第一段**：能力服务出判定（规则表指纹 + 命中规则 + 逐条结论） |
| `submit(...)` | **第二段**：启动编排；低风险直接办结；中/高风险停在人工节点并登记待办 |
| `pending(role, status)` | 按角色/状态取待办（网关与主管视图的数据源） |
| `decide(run_id, decision, actor, role, note)` | **审批主入口**：原子认领 → 审计 → 写回路由字段 → 同步恢复 → 完结待办 |
| `recover_on_startup()` | 启动补偿：扫描暂停 run，补建待办并写"重新通知"审计 |
| `status(run_id)` | 单 run 全景（状态/风险/命中规则/占用/待办/审计链） |
| `metrics()` | 指标（待办量、在办 run、决策分布、规则与法规指纹） |

**三条硬约束的落实方式**：

1. **审批只生效一次** → `runtime_store.claim_run`（单条 `UPDATE ... WHERE status='paused' AND claimed_by IS NULL`），
   断网/并发/跨进程都只有一个赢家；`finally` 里释放占用。
2. **恢复必须可靠** → 一律走**同步路径**（`WorkflowRunner.resume` + `_update_run_from_result`），
   不用框架线程池恢复（D0-G3 实测该路径在跨进程场景下 run 记录会停滞）。
3. **重启后仍要有人收到提醒** → `recover_on_startup()`（框架本身没有该能力，D0 实读：`list_pending_runs` 无生产调用点）。

## 2. 本阶段新增的框架纪律（第 6 条）

P3 已固化 5 条；P4 又实测到 1 条，已写入 `workflows/compliance_review.json` 的 `_comment`：

> **6) human 节点的"自环"会让后续 resume 的值被下游 human 节点消费。**
>
> 现象：`specialist_review --modify--> specialist_review`（自环）时，
> 专员第二次 `confirm` 的 resume 值被**主管节点**吃掉，流程直接办结、跳过主管复核。
> 实测状态证据：`supervisor_note` 变成了 `confirm`，`next=[]`。
>
> 修复：循环边必须**经过一个普通节点**再回到 human（本图 `modify → entry_probe → specialist_review`），
> 这样每次 resume 都能准确投递到当前等待中的那个节点。修复后实测回到 `supervisor_review` 正常暂停。

这是在"人工改单后二次确认"这种非常常见的业务形态上会踩到的坑，属于必须记录的硬约束。

## 4. 运维工具（本阶段顺带补齐）

自检会持续产生 run 与待办，长期累积会污染指标与待办视图。因此补了两个显式工具：

| 工具 | 用途 |
|---|---|
| `scripts/tools/cleanup_runs.py` | 按状态/前缀清理 run（连带 checkpoint 与待办），支持 `--dry-run` |
| `scripts/tools/status_overview.py` | 一眼看清在办 run、待办、决策分布；`--run <id>` 可看单条完整审计链 |

实测：清理一次即把"暂停中的 run"从 20 降到 0，指标恢复可读。
