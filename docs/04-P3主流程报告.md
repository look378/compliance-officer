## 1. 主流程 spec（`workflows/compliance_review.json`）

```
START → entry_probe(无副作用分诊节点)
          ├─(overall_risk_level=low)──→ finalize ──→ END
          └─(mid|high)──→ specialist_review(人工#1)
                            ├─(confirm)──→ supervisor_review(人工#2) ──→ finalize
                            ├─(modify)───→ specialist_review（重标注后再次确认）
                            └─(reject)───→ finalize
```

- **第一段（能力服务）**：`annotate_document` 输出判定与证据（规则表指纹、命中规则、逐条结论、解析置信度）。
- **第二段（本图）**：以判定为初始状态进入编排；分诊、人工审批、归档每一步都有 checkpoint 与审计事件。

## 2. 本阶段发现并固化的 5 条框架纪律（全部实测得出）

这一节是本阶段最有价值的部分。每条都写进了 spec 的 `_comment`，成为后续所有工作流的硬约束。

| # | 纪律 | 现象与代价 | 依据 |
|---|---|---|---|
| 1 | **工具名必须用注册后的完整名** `mcp__<server_id>__<tool>` | 写裸名 `parse_contract` 时，工作流运行得到「❌ 工具不存在」，且该错误字符串会**静默进入状态**继续往下跑 | `nodes.py` 的 tool 节点按名查 `tools` 字典；MCP 工具注册名带前缀 |
| 2 | **tool 节点把结果转成字符串** | 结构化判定落到状态里是 JSON 文本；服务端若按 dict 读取会全部拿不到，条件边随之失效 | `nodes.py:100` `str(result)` |
| 3 | **human 节点在条件边之前执行** | 期望"低风险跳过人工"时，人的节点会先 interrupt，后面的条件边根本没机会执行 | 实测：节点定义顺序决定 super-step 内执行次序 |
| 4 | **不支持从 `START` 出发的条件边** | 直接报编译错误 `Found edge starting at unknown node 'START'` | `builder.py:85` 只做 `START` 字面量替换，条件边未替换 |
| 5 | **同一 super-step 内服务端 `update_state` 对条件边不可见** | 条件边读到的是该 super-step 开始时的快照；注入无效 | 实测：注入 `overall_risk_level` 后条件边仍走兜底分支 |

**由这 5 条推出的设计决策（两段式执行）**：

> 判定由能力服务完成（可重复、可审计、带版本指纹），编排由图完成（可 checkpoint、可人工介入）。
> 这不是权宜之计：它同时满足"确定性环节不交给模型自由裁量"与"人工审批必须可恢复"两条要求。

## 3. 四条流程路径的证据

| 路径 | 输入 | 步骤 | 结果 |
|---|---|---|---|
| A 低风险 | 技术服务合同（无风险条款） | 1 步 | `completed`，**0 个人工节点** |
| B 中风险 | 含"违约金 50%"条款 | 3 步 | 暂停(专员) → 暂停(主管) → `completed` |
| C 高风险 | 含保本/无条件解除/超时工时/免同意收集 | 4 步 | 暂停(专员) → modify+重标注 → 暂停(专员) → 暂停(主管) → `completed` |
| D 驳回 | 中风险合同 | 2 步 | 暂停(专员) → reject → `completed`，产出提案 `RP-*`（kind=new），**规则表指纹不变** |

每条路径的实际状态都留在证据文件里（`cases.A_low_risk` / `B_mid_risk` / `C_high_risk_cycle` / `D_reject_path`），
包括：步骤序列、风险等级、命中规则、决策记录（含审计 ID 与待办完结）、提案编号。

**高风险用例的命中规则**：`RR-001, RR-003, RR-004, RR-005, RR-008` —— 即保本收益、最终解释权、
无条件解除、超时工时、免同意收集个人信息，与规则表的期望一致。

## 5. 对后续阶段的输入

### P4（人工闭环服务端化）

1. 把本阶段脚本里"服务端扮演"的部分固化为正式模块：两段式执行的编排器 + 待办消费 + 审计写入。
