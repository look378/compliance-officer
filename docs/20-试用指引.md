# 试用指引 · 合规官「小合」（30 分钟走完全流程）

> 目标：你作为**企业用户**，用浏览器把数字员工真用一遍 —— 提交合同、走人工签核、
> 审批规则提案、和数字员工对话，并看到每一步留下的证据。
>
> 全程只需要浏览器 + 两条命令。技术栈见 `docs/19-技术栈清单.md`，审查结论见 `docs/18-第二次审查报告.md`。

## 0. 两条命令（在本项目目录下执行）

```powershell
cd <本仓库所在目录>        # 例：D:\work\compliance_officer

# ① 一键准备：起服务 + 跑三组可用性自检（推荐首次加 -Reset，先把自检遗留数据清干净）
pwsh -File scripts\trial-demo.ps1 -Reset

# ② 试用结束后停止服务
pwsh -File scripts\stop-demo.ps1
```

`trial-demo.ps1` 会做四件事，跑完**服务保持运行**：

| 步骤 | 内容 | 通过标准 |
|---|---|---|
| 0（可选 `-Reset`） | 清理自检遗留：取消 762 个暂停 run、清空待办、删除 33 个测试账号（保留 admin/zhangsan/lisi） | 打印各项条数 |
| 1 | 启动演示环境：能力服务 8770 + Mock 外部系统 8780 + 网关 8790 | 三个 `/health` 都 OK |
| 2 | 业务流自检（网关 12 项）：提交→待办→双签→越权拦截→指标→SSE | 12/12 |
| 3 | 工作台可用性自检（30 项）：页面元素、页面引用的每个接口、上传、权限矩阵 | 30/30 |
| 4 | 生产化自检（12 项）：身份/账号生命周期/配置门禁/审计台/日志/**数字员工对话** | 12/12 |

看到 `[trial] 全部通过 —— 可以直接开始试用。` 就可以打开浏览器了。
若某步失败：服务仍在运行，页面对应功能可照常试，把那一条失败信息发我即可。

> 不想等自检：`pwsh -File scripts\trial-demo.ps1 -Reset -SkipChecks`（只起服务，约 10 秒）。

## 1. 打开工作台并登录（10 秒）

浏览器访问 **http://127.0.0.1:8790**

右上角 **「认证设置」** → 令牌填 `local-dev-token`，角色选 **specialist** → 保存。

> 为什么要填令牌：这是**演示模式**（`AUTH_MODE=demo`），用固定令牌模拟"已登录的某角色"，
> 方便你**随时切换身份看权限差异**，不需要真的建账号。
> 生产模式（`AUTH_MODE=jwt`）则需要账号密码登录，企业 SSO 模式（`AUTH_MODE=sso`）走公司 IdP —— 见 `docs/15-企业SSO对接.md`。

**切换角色**：改「认证设置」里的角色即可（specialist / supervisor / admin）。请在每个场景里留意
"同一个页面，不同角色看到的按钮/菜单不一样"——这就是权限矩阵在工作。

## 2. 场景①：低风险合同 → 全自动办结（1 分钟）

**位置**：`合同审查台`

1. 点 **「低风险示例」**（示例文本会自动填进输入框）
2. 点 **提交审查**

**应该看到**：

| 字段 | 期望值 | 含义 |
|---|---|---|
| `status` | `completed` | 已办结 |
| `risk_level` | `low` | 低风险 |
| `paused` | 空 | **没有生成任何待办** |

**这一步证明**：干净合同不惊动任何人，自动出报告 —— 数字员工不是"什么都转人工"。

顺便看一眼：`待办审批` 里**没有**这条记录（这是正确的）。

---

## 3. 场景②：中风险合同 → 专员初审 + 主管复核（5 分钟，核心场景）

**位置**：`合同审查台`

1. 点 **「中风险示例」**（含"违约金 50%"条款）→ 提交
2. **应该看到**：`status=paused`，`risk_level=mid`，暂停在 **合规专员** 节点

### 3.1 专员这一步

3. 切到 `待办审批`，角色 = **specialist**
4. 找到这条待办 → **认领** → 填意见 → **确认**
   - **应该看到**：流程继续，但**没有结束** —— 它转到"主管复核"了
   - 这一步体现了设计的核心：**一个角色不能一步办结**

### 3.2 故意越权（值得试，30 秒）

5. 保持角色 = specialist，回到 `运行概览`，对这条 run 点 **通过/批准**
   - **应该被拒绝（409）**，提示"决策与当前等待节点不匹配"
   - 这防的是**伪造主管签核**：专员不能替主管签字

### 3.3 主管这一步

6. 把角色切成 **supervisor** → 回 `待办审批` → 通过 → 归档
   - **应该看到**：`status=completed`

### 3.4 看证据链

7. 进 `运行概览` → 点开这条 run → 看到**完整事件序列**：
   `review_submitted` → `todo_created` → `human_decision` → `todo_completed` → … → `review_archived`
   每一跳都有**谁、什么时候、什么角色、什么决策**。

8. 生成/查看报告（`合同审查台` 或 run 详情）：`.md` 与 `.pdf` 两种形态，
   路径形如 `reports/RPT-<时间戳>-<短哈希>.pdf`

**这一步证明**：合规审批要的"谁该做什么、谁做过了、只做一次、留痕"四件事都在。

## 4. 场景③：规则提案 → 主管批准 → 版本化生效（5 分钟）

**位置**：`规则提案`（角色 specialist 可提，supervisor 可批）

1. 角色 = **specialist**，提交一条提案：指出某类条款有问题 + 给出识别模式 + 关联法条
2. **应该看到**：系统做**去重判定** —— 与现有规则**完全相同**→ 转"修订"；
   **包含关系**→ 提示相似；**同模式不同等级**→ 转"冲突，需主管裁决"；确实是新的→ 走"新增"
3. 角色切 **supervisor** → 批准
4. 回 `规则库`：该规则**版本号 +1**，并记录批准人/时间/变更说明

**这一步证明**：人工驳回的原因**不会**被直接写成规则（那样会污染判定），
而是走"提案 → 去重/冲突裁决 → 批准 → 版本化"的治理闭环，下次同类条款自动命中。

> 想看它"当场学会"：先用违规条款提交一份合同（走人工 → 驳回），再把驳回原因提成规则提案并批准，
> 然后**再提交同一份合同** —— 这次它会自己命中新规则。

## 5. 场景④：和数字员工对话（2 分钟）

**位置**：`员工对话`

试着问（这几句都测过）：

- 「规则表里"最终解释权"这类条款为什么有风险，依据哪条法条？」
- 「刚才那单合同为什么判成中风险？命中了哪条规则？」
- 「《劳动法》对月加班时长上限是怎么规定的？」

**应该看到**：回复里带**规则编号（RR-xxx）或法条出处**，并且**显示它调用了哪些工具**
（例如 `mcp__compliance__search_regulations`、`mcp__compliance__annotate_clause`）。

**这一步证明**：数字员工不是纯聊天 —— 它的回答来自**本项目的 15 个岗位工具**（检索/标注/规则/待办），
所以有据可查，而不是模型自由发挥。

## 6. 其它值得点的地方（各 1 分钟）

| 页面 | 看什么 |
|---|---|
| **运行概览** | 每次审查的完整证据链；SSE 实时事件流（提交一份合同就能看到事件一条条冒出来） |

| **规则库** | 规则表版本演进（谁改的、改了什么、为什么） |

## 7. 如果你看到不对（排查顺序）

| 现象 | 先看这里 |
|---|---|
| 页面打不开 | `netstat -ano \| Select-String ':8790\s+.*LISTENING'`；看 `.runtime\logs\gateway.err.log` |
| 页面能开但接口 401 | 「认证设置」里令牌/角色没保存成功 —— 重填 `local-dev-token` |
| 接口 403 | 当前角色权限不够（这是**正确行为**）：切到 supervisor / admin 再试 |
| 提交合同报错 | 能力服务是否在线：`http://127.0.0.1:8770/health`；看 `.runtime\logs\capability.err.log` |
| 员工对话回复慢 | 它在真实调用大模型（DeepSeek），通常 3–10 秒，属正常 |
| 待办列表不干净 | 跑一次重置：`.\.runtime\venv\Scripts\python.exe scripts\tools\cleanup_runs.py --trial-reset` |
| 想从头再来 | `pwsh -File scripts\stop-demo.ps1` 然后重新 `trial-demo.ps1 -Reset` |

## 8. 试用时可以顺手验证的"硬事实"

这些都是本机实测过的（证据在 `docs/evidence/` 与 `docs/17-本机真实验证记录.md`）：

- **规则判定不依赖大模型**：判定路径是"规则表（正则 + 版本）+ 法规检索（中文 2-gram）"，
  所以可复现；评测基线：风险召回 **1.00**、误报 **0**、等级一致性 **1.00**、表格单元格准确率 **100%（11 例）**、人工介入率 **0.76**
- **真实 OCR**：扫描版 PDF（整页位图、无文本层）能被真实识别出中文条款并命中风险（引擎 RapidOCR）
- **真实 PostgreSQL 16.4**：`DB_MODE=pg` 时本项目自有表真的落 PG（18/18 通过）
- **真实 OIDC 单点登录**：本地 IdP 走完 discovery → PKCE → ID Token 严格校验 → 组映射角色（20/20 通过）
- **底座完整性**：110 个文件与 SHA256 基线完全一致（依赖没有被就地改动）

## 9. 试用**不在**范围内的部分（提前说明，避免误判）

1. 真实企业 OA / 合同库 / 邮件网关的**现场字段名与鉴权**未对接（连接器已就绪，`CONTRACT_SOURCE=dir|http`、`MAIL_GATEWAY=http|smtp`）。
2. 贵司 IdP 的现场联调未做（本机用的是标准 OIDC 本地 IdP）。
3. 多实例部署（当前是单实例；SSO 的一次性 state 在进程内存）。

这三项都是"需要贵司环境才能做"的事，不是已知缺陷 —— 详见 `docs/18-第二次审查报告.md` §6；容器交付形态已实测通过（见 `docs/17` §4）。
