## 1. 关键结论（先说会影响架构的）

### 1.1 岗位能力通道确认为「自建 MCP 服务」（G4 通过，8/8）

- 自建 MCP 服务（本项目进程，`mcp_server/compliance_mcp_server.py`）被框架完整接入：
  握手成功、协议 2025-03-26、4 个工具发现并注册为 `mcp__compliance__*`。
- 三个标注用例全部正确：`high` / `mid` / `low`，命中规则带 `rule_id` 与法条引用，
  低风险用例不产生任何无引用风险（"无引用不判风险"生效）。
- **主 Agent 工具总数从 36 增至 40**，新增的 4 个全是 `mcp__compliance__*`
  —— 这是"零改动接入岗位能力"的直接证据。

### 1.2 框架的 HITL 恢复必须自己做互斥（G6 实测，且发现了框架行为异常）

- **竞态真实存在**：无抢占时，4 个并发 `resume` 请求**全部被接受**（`accepted=4`）。
  原因是框架的 `resume_run` 是「读状态 → 判断 paused → 提交后台任务」，读与提交之间没有原子性。
- **补救有效**：本项目在自身代码里实现原子抢占（`UPDATE ... WHERE status='paused' AND claimed_by IS NULL`），
  并发线程 4 → 接受 1，跨进程 2 → 接受 1。
- **额外发现（框架行为异常，需在 P4 规避）**：跨进程恢复时，
  `manager.resume_run` 的线程池路径会把 checkpoint 正确推进到完成、
  也会发出 `loop_kind=completed` 总线事件，但 **`workflow_runs` 记录可能长时间停留在 `paused`**；
  同一进程内改用同步路径（`WorkflowRunner.resume` + `_update_run_from_result`）则能可靠写为 `completed`。
  → **决策：服务端恢复入口统一采用「原子抢占 + 同步恢复」，不复用框架的线程池恢复路径。**

### 1.3 人工节点的通知与恢复必须由本项目兜底（G3）

- 框架发出的暂停通知确实是普通总线事件（`langgraph_loop`），内容里带 `run_id`，
  并明写「回复时请带上 {run_id}」——即**依赖用户手动回填**，与前期实读结论一致。
- 本项目已在 G3 中验证自己的恢复路径：抢占 → 同步恢复 → 状态 `completed` →
  **第三个全新进程可读到 `completed` 与完整终态值**（`decision=continue`、`note=睡眠完成…`）。

### 1.4 OCR 档位定档：无 OCR 模式（G5）

- 环境实测：`pdfplumber` / `pypdf` / `python-docx` / `Pillow` 可用；
  **`paddleocr`、`rapidocr_onnxruntime` 均未安装**。
- 用自造测试件验证了关键前提：原生文本 PDF 可提出 **120 个中文字符**（用系统微软雅黑，非方块乱码）；
  图片型 PDF（无文本层）提取字符数 **0** —— 证实扫描件确实需要 OCR，不是解析器问题。
- **档位决策**：
  - 默认 **无 OCR 模式**（`ocr_tier=none`）：支持原生文本 PDF / Word；
    扫描件标记低置信度走人工通道（人工通道本就存在，零额外成本）。
  - 完整 OCR 需要约 600MB 级依赖 + Windows VC++ 运行库，且 CPU 推理慢；
    待出现真实扫描件需求时按 `PaddleOCR → RapidOCR → 无 OCR` 顺序升级。
  - **该决策不阻塞主链路**：解析档位是运行时配置，升级时改一处依赖即可。

### 1.5 标注质量基线建立（G7）

| 指标 | 结果 |
|---|---|
| 预埋风险命中率 | **5/5 = 1.00** |
| 误报率 | **0/2 = 0.00** |
| 引用完整性（无引用不判风险） | **通过** |

> 口径纪律：本基线**只覆盖确定性规则通道**，不含 LLM 泛化与表格抽取。
> 三类指标在 P2/P7 必须**分开报告**，不得合并成一个"准确率"。

### 1.6 唯一未通过项：G4b 技能确定性脚本通道

- **现象**：框架的 `/skills setup` 用 `python -m venv` 创建技能隔离环境；
  实测该 venv **没有 pip**，随后 `python -m pip install` 报 `No module named pip`，安装失败。
- **成因（代码事实）**：框架调用的是 `venv` 而非 `venv --seed`（`agent/skill/manager.py:376-379`），
  在 Python 3.13 上该 venv 默认无 pip；同时框架用管道捕获子进程输出（`capture_output=True`），
  在受限环境中进一步受限。
- **已定档降级**：**确定性执行通道改由 MCP 工具承载**（G4 已通过，能力等价且更可测）。
  技能包继续作为「岗位 SOP 说明书」使用（G4b 证据显示技能全文注入正常，
  含关键约束「无引用不判风险」「禁止静默覆盖」，摘要 405 字符、活跃正文 1559 字符）。
- **影响面**：不影响主链路，仅意味着"把重依赖脚本塞进技能包"这条路在本机受限环境下不可用。

> 本次 G2 第一版实现即踩到该坑，修正拓扑后全部通过。
