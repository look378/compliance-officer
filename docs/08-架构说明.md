## 1. 一句话架构

**岗位能力服务（本项目） + 运行时框架（独立进程、源码零改动） + 轻量网关 + Mock 外部系统**，
四者通过配置连接，业务状态单一真相源在编排器与工作流状态里。

```
                  ┌──────────────── 输入 ────────────────┐
   Mock OA 收件目录 ─┐                                    │
   飞书 / 终端      ─┼─→ 运行时框架进程（LemonClaw，源码零改动）
   Webhook / 网关   ─┘        │ 主 Agent · 工作流 · 技能 · 渠道
                              │ mcp__compliance__*（15 个岗位工具）
                              ▼
                  ┌──────── 岗位能力服务（本项目进程，:8770）────────┐
                  │ 工具契约层 tools_registry                       │
                  │ 合同解析 · 法规检索 · 规则判定 · 报告生成        │
                  │ 规则库（唯一真相源 YAML + 提案审批）             │
                  │ 统一待办队列 + 审计事件 + 运行态互斥原语         │
                  └───────────────┬────────────────────────────────┘
                                  │
        ┌─────────────────────────┼──────────────────────────┐
        ▼                         ▼                          ▼
  编排服务（本进程内）        轻量网关(:8790)            Mock 外部系统(:8780)
  两段式执行 · 待办消费      认证/RBAC/待办/指标/SSE      OA 文件 · 邮箱 · 故障注入
  原子认领 · 启动补偿
```

## 3. 关键设计决策（含取舍理由）

### 3.1 运行时框架源码零改动

- 所有岗位能力放在本项目进程，通过框架原生的 **MCP 工具**机制接入（注册为 `mcp__compliance__*`）。
- 收益：可 diff 验证（110 个源文件 SHA256 基线）、可跟随上游更新、职责边界清晰。
- 代价：需要遵守框架的若干硬约束（见 §4）。

### 3.2 两段式执行（判定 → 编排）

第一段由能力服务出判定（可重复、带规则表指纹与命中规则）；第二段由图做分诊、人工审批、归档。

**为什么必须这样切**（P3/P7 实测）：
1. 框架的 `tool` 节点会把结果转成字符串，且**不产生 checkpoint**，同一 super-step 内条件边读到的是该步开始时的快照；
2. 若把判定塞进图里再路由，服务端注入的判定值对同一步的条件边不可见。

两段式同时满足"确定性环节不交给模型裁量"与"人工审批可 checkpoint 恢复"。

### 3.3 路由字段与人工节点输出字段分离

框架会把 `resume` 的值写入**当前等待的 human 节点**的输出字段。若让该字段兼任条件边路由键，
就会出现"同一个值被写进多个字段"——实测事故：专员 confirm 后主管节点被写入 confirm，
而主管 mapping 首键 `approve` 静默兜底 → **主管复核被跳过、流程直接办结**。

因此：**路由只依赖 `detail_decision`**（非人工输出字段），人工输出字段（`specialist_note`/`supervisor_note`）只作记录。

### 3.4 恢复与互斥由本项目负责

| 缺口（框架现状） | 本项目补位 |
|---|---|
| 人工节点只发文本通知，run_id 靠人肉回填 | 统一待办队列，服务端用待办里的 run_id 恢复 |
| 无待办表、无投递确认 | `compliance_todo` + 审计事件 + 启动补偿重新通知 |
| `resume_run` 读状态与提交线程池之间无原子性 | `runtime_store.claim_run` 原子抢占（线程/跨进程各只生效一次） |
| 线程池恢复路径在跨进程场景下 run 记录停滞 | 一律走**同步恢复**路径 |

### 3.5 数据库：默认 SQLite，交付形态 PG

场景边界是"低频高价值"（日均 <100 份、审批角色 ≤10 人），单实例完全够用。
`docker-compose.yml` 提供 PostgreSQL 16 + pgvector 的交付形态；本地开发用单库 SQLite（一键拉起、无依赖）。
运行时框架自身的 checkpoint 仍留在 SQLite（本项目不替换框架存储层）。

## 4. 必须遵守的框架硬约束（实测汇总）

写在这里，供任何后续改动对照。完整版见 `workflows/compliance_review.json` 的 `_comment`。

| # | 约束 | 后果 |
|---|---|---|
| 1 | MCP 工具名必须是注册后的完整名 `mcp__<server_id>__<tool>` | 写裸名得到「❌ 工具不存在」，且该字符串会静默进入状态 |
| 2 | 一个节点要么静态出边、要么条件边 | 两者同挂 → 多个 pending task → "state 已完成但 run 仍 paused" |
| 3 | 条件边未命中 mapping 按**第一个键**兜底 | 兜底键语义必须安全 |
| 4 | human 节点按定义顺序先于条件边执行 | 想"按风险绕过人工"必须用无中断的前端节点分诊 |
| 5 | 不支持从 `START` 出发的条件边 | 编译报 `unknown node 'START'` |
| 6 | human 节点自环会让后续 resume 被下游节点消费 | 循环边要经过普通节点 |
| 7 | tool 节点结果被转成字符串、且不产生 checkpoint | 结构化结果需反序列化；同一步注入的状态对条件边不可见 |
| 8 | `resume` 的值写入当前等待节点的输出字段 | 路由字段必须与人工输出字段分离（见 §3.3） |

## 5. 数据流（一次审查）

```
1. 受理          intake()：annotate_document → 判定 + 命中规则 + 规则表指纹
2. 编排启动      submit()：以判定为初始状态进入工作流
                 · 低风险 → finalize → 归档（不惊动人）
                 · 中/高风险 → 停在 specialist_review，登记专员待办 + 审计
3. 专员决策      decide()：原子认领 → 审计 → 写 detail_decision → 同步恢复 → 完结待办
                 · confirm → etl_gate → supervisor_verify（登记主管待办）
                 · modify  → 服务层重新标注 → 回分诊 → 再次确认
                 · reject  → finalize（服务层生成规则提案，进主管待办）
4. 主管签署      decide(approve) → etl_gate → finalize → 归档
5. 规则演进      提案 → 主管审批（run 级与提案级两层互斥）→ 版本化写入 YAML → 同类条款再次命中
6. 主动工作      Cron → 巡检收件目录 → 幂等发起审查 → 邮件通知；材料缺失 → 自排跟进任务
7. 证据链        每步写 compliance_audit；status_overview 可查单 run 完整链路
```

## 6. 部署形态

| 形态 | 说明 |
|---|---|
| **本机开发（当前已验证）** | `.runtime/venv` + 单库 SQLite + 三个 Python 进程（能力服务/网关/Mock），一键脚本拉起 |
| **交付形态（docker-compose）** | capability(:8770) + gateway(:8790) + mock(:8780) + postgres(pgvector:pg16)；运行时框架按项目纪律独立部署并通过 `mcp.json` 连接能力服务 |

> 本机无 Docker、无管理员权限，因此交付形态只做**文件级与语法级**验证（见验收清单第 9 项）。
