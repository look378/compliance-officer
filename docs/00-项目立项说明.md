## 2. 第一原则：运行时框架源码零改动

### 2.1 边界定义

| 允许 | 禁止 |
|---|---|
| 在 `.lemonclaw/` 下写配置、Skill 包、`mcp.json` | 修改框架源码目录内任何文件 |
| 以独立进程提供岗位能力（MCP server） | 修改框架的 DAO / 主循环 / 工作流 / 渠道实现 |
| 通过框架原生扩展点接入（Skills、MCP、Cron、workflow spec） | 依赖框架中"已声明但未实现"的能力 |
| 复制框架的部署产物（`.lemonclaw/`） | 复制并修改框架源码 |

### 2.2 为什么这样切（三条理由）

1. **可验证**：对框架目录做哈希/diff，"未重写框架"从一句声明变成可复核事实。
2. **可更新**：上游修复与新增能力可平滑吸收，不会被本项目的改动锁死。
3. **聚焦差异化**：岗位化的价值在岗位知识、证据链与评测，不在重写中间件；重写中间件与项目B 的展示面重复。

### 2.3 需要放弃的东西（诚实清单）

- 不引入 PostgreSQL 版的 LangGraph checkpoint（框架的 checkpoint 留在 SQLite，与业务库解耦）。
- 不替换框架的记忆/技能存储层（改用"法规走自建向量检索、岗位经验走框架记忆"的分工）。
- 因此本项目**不做**"框架级 SQLite→PG 全域迁移"这一项（原任务书 §3.1 的主体工作）。

> 决策影响：原任务书铁律 2 与 `AGENTS.md`「保持现有设计不变」的直接冲突被消除；原 §3.1/§3.2 的工程预算整体转移到岗位知识与评测。

## 3. 岗位能力形态（三通道分工）

明确"哪类能力由什么承载"，避免把确定性流程交给模型自由裁量：

| 通道 | 承载内容 | 理由 |
|---|---|---|
| **MCP 工具**（本项目进程） | 合同解析、表格抽取、法规检索、风险标注、报告生成、规则提案 | 确定性、可单测、可版本化；经框架原生机制注册，零改动 |
| **Workflow spec**（本项目声明式 JSON） | 编排、条件分支、人工节点、循环边 | 复用框架的 HITL 与 checkpoint，不写代码 |
| **Skill 包**（本项目 `skills/`） | 岗位 SOP、判定口径、输出模板（说明书性质） | 让主 Agent 在对话场景下具备岗位语感 |

> **为什么不用 Skill 脚本作为主要执行通道**：框架的技能正文注入有单技能 10000 字符**砍中间**的上限、且注入时**不解析密钥占位符**，长法规与 SOP 不适配；技能脚本执行默认关闭且需人工安装依赖。确定性环节走 MCP 工具更稳。

## 5. 阶段门禁（D0 不通过则止损）

D0 的目标不是"跑通框架"，而是**证明这个技术选型能承载合同审查**。任一门禁不通过，立即上报并切换预案，不进入业务实现。

| 门禁 | 验证内容 | 不通过的含义 |
|---|---|---|
| G1 | 主流程闭环：受理 → 解析 → 检索 → 标注 → 人工暂停 → 带 run_id 恢复 → 报告 | 编排能力不足 |
| G2 | 图形状：条件边分流 + 循环边收敛 + **两个连续人工节点**独立暂停/恢复 | 主工作流形态不成立（原任务书 D0 未覆盖） |
| G3 | 断点续接：暂停态强杀进程 → 重启 → 恢复成功并重新通知到人 | 恢复不可用需补关键模块 |
| G4 | 能力通道：自建 MCP server 注册成功且可调用 | 岗位能力无法零改动接入 |
| G5 | OCR 档位：优先高精度方案，失败降级轻量方案，再失败启用无 OCR 模式（仅原生文本 + 扫描件转人工） | 输入通道受限 |
| G6 | 并发互斥：两个入口同时 resume 同一 run，仅一次生效 | 需先补原子状态抢占 |
| G7 | 解析质量：含表格合同的结构化抽取准确率（人工抽检） | 岗位能力不达交付线 |
